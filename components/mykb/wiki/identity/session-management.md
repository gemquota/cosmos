# Session Management

## Summary

Session management is the practice of maintaining authenticated state between the browser (or client) and the server after login. A session identifier binds an otherwise stateless HTTP conversation to a user identity, with defined creation, renewal, and termination rules. It matters because most web attacks — session fixation, hijacking, replay — are failures of session lifecycle: predictable IDs, overlong lifetimes, or logout that does not actually invalidate the session. OWASP's Session Management Cheat Sheet is the canonical checklist, and RSIS3's session handling should be measured against it.

## Details

- Session ID properties: generated by a cryptographically secure PRNG, at least 128 bits of entropy, unique per user, and never placed in URLs or logs.
- Transmission: session cookies should carry HttpOnly, Secure, and SameSite attributes; tokens should travel only over TLS and be bound to the client context.
- Lifecycle controls: idle timeout, absolute timeout, re-authentication for sensitive actions, and explicit logout that deletes both client and server session state.
- Storage: server-side session stores enable instant revocation; stateless JWT sessions trade that control for scale and need careful expiry and revocation design.
- Common failures: accepting session IDs from multiple sources, not rotating IDs after login, and treating token expiry as logout.
- For mykb, session management governs both human web sessions and agent sessions in the session-state machine, so one consistent policy file is worth maintaining.
