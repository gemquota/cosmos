# Tokenization and Masking

## Summary
Tokenization and masking both replace sensitive values with safer representations while keeping data usable: tokenization swaps a value for a random token held in a secure vault, and masking obscures values for non-privileged users while preserving format. They are the privacy-by-design tools that let teams work with realistic-looking data without exposing real PII.

## Details
- Tokenization: a sensitive value (a credit card number, email, national ID) is replaced by a random token; only the tokenization vault maps token back to original, and the mapping is the crown jewel that must be protected. Formats can be preserved — a 16-digit card number becomes a different 16-digit number — so downstream systems keep working unchanged.
- Masking: static masking rewrites data at rest (a database copy for test has emails turned into `user1@example.com`), while dynamic masking rewrites at query time so raw data never leaves the source. Warehouses commonly apply dynamic masking policies per role: support staff see `4321 **** **** 5678`, auditors see the full value.
- Concrete examples: a payments team that stores card numbers in a vault and only ever moves tokens through applications and analytics; a data warehouse where dynamic masking lets analysts join on masked customer IDs while admins unmask on demand; and synthetic test data generated by masking production snapshots so QA exercises realistic volume and shape.
- Failure modes: vault compromise defeats tokenization (the tokens are just references); tokens that are guessable or derived from the input leak information; masking that preserves too much structure (keeping postal codes and birth dates) re-identifies people; and per-role masking policies that are misconfigured expose raw data to the wrong role.
- Tradeoffs: tokenization preserves referential integrity and is reversible by design, but every lookup goes through the vault (latency, scaling, availability risk); masking is cheap and non-reversible for the masked role, but format-preserving masking can be weaker cryptographically and joins on masked values can reveal correlation.
- Operational practice: classify data first so you know what must be tokenized or masked; protect the vault with the same rigor as the original data; test that masked data preserves the distributions your analytics depend on; and audit unmasking events.
- RSIS3/mykb relevance: any loop that stores personal data needs the tokenize-vs-mask decision; this node keeps the tradeoffs and failure modes retrievable so privacy choices are deliberate, not incidental.
