# Requests Pages

## Summary
Requests pages are where work gets formally requested — a new article, a review, a fix — with enough structure that the request is actionable without a conversation. They are the intake layer of a curated knowledge workflow: a good request becomes a tracked task; a vague one becomes a queue zombie.

## Details
- **Anatomy of a good request** — a deliverable (what will exist when done), a motivation (why it matters), and acceptance criteria (how done is recognized); links to related material instead of inline essays.
- **Actionable without conversation** — the test of a request is whether a competent worker can start from the page alone; any request that needs a clarifying chat is incomplete.
- **Routing** — requests move through triage into task lists, where they gain an owner and a priority; the requests page is the entry point, not the end state.
- **Failure modes** — vague requests, requests without owners, and requests that never leave the intake state; each converts a healthy pipeline into a backlog.
- **Relationship to noticeboards** — noticeboards announce issues to the community; requests pages formalize one of those issues into a shape that can be executed.
- **Relationship to review** — completed requests feed review queues, where the output is checked before it is accepted into the wiki.
- **mykb relevance** — the wiki's curation workflow uses requests pages as the intake layer, connecting triage, task lists, and review queues.

- **Lifecycle states** — requests pages work best with explicit states: drafted, triaged, assigned, in progress, done, rejected; a request without a state cannot be managed and quietly becomes stale.

- **Request templates** — a small template (goal, scope, acceptance criteria, links) standardizes intake and makes triage fast; the template is the contract between requester and worker.
