# 301 vs 302

## Summary
301 Moved Permanently and 302 Found are the two redirect codes that dominate the web, and their difference is not just semantic: it changes browser caching, link-equity behavior, and how HTTP methods are preserved across hops. Understanding the tradeoff between permanent and temporary redirects is a prerequisite for designing clean URL migrations, login flows, and API aliases.

## Details
- Mechanism: a 301 tells the client the resource has a new permanent home. Browsers and HTTP caches may store the mapping and future requests for the old URL go straight to the new one without hitting the server, and search engines transfer ranking signals. A 302 signals a temporary detour: the mapping is not cached by default, the original URL stays authoritative, and clients should keep asking the original location next time.
- Method behavior: the classic gotcha is that browsers historically rewrote a POST to GET on 302, which breaks form submissions and payment flows. The HTTP spec later clarified that 301 and 302 permit the method change, while 307 Temporary Redirect and 308 Permanent Redirect guarantee method and body preservation. APIs that redirect POSTs must use 307/308 or design the flow so the client retries at the new endpoint explicitly.
- Concrete examples: renaming an endpoint from `/v1/users` to `/v2/people` calls for 301 so caches and crawlers converge on the new path; a scheduled maintenance banner or a transient A/B experiment should use 302 so nothing caches the detour; OAuth login handoffs that bounce through an intermediary almost always want 302 because the target may change per request.
- Failure modes: using 301 for a redirect you later revert is painful because intermediaries cache the permanent mapping beyond your control, and you may need `Cache-Control: no-store` on the redirect to reclaim it. Redirect loops (A to B to A) burn request budget and confuse clients; missing `Location` headers make the response useless; and redirecting error pages to the home page hides failures from both users and monitoring.
- Operational tradeoffs: 301s reduce repeat traffic and are good for canonicalization, but they make rollback slow; 302s are flexible but add an extra round trip on every request and can leak URL parameters into logs and referrer headers. For API clients, decide per route: permanent contract changes get 301 or 308, transient states get 302 or 307.
- RSIS3/mykb relevance: memory layers like MyKB rely on stable identifiers; if a knowledge article is relocated, a permanent redirect at the lookup layer keeps old wikilinks resolving, while a temporary redirect signals a reindexing pass rather than a permanent move.
