# 404 vs 410

## Summary
404 reports a URI that does not exist; 410 Gone reports a URI that existed and is now intentionally gone. The distinction controls link hygiene, cache behavior, and client expectations.

## Details
404 Not Found means the server cannot map the request target to a resource, either because it never existed, the path is wrong, or the server deliberately hides it. 410 Gone (RFC 9110) means the resource was deliberately removed with no forwarding address. Both are terminal client errors, but 410 carries the semantic "this was here and will not return," which lets search engines and clients drop the link instead of re-checking it on schedule.

Mechanically the decision is: does the URI name something that existed? A deleted product page, a retired API endpoint, or a decommissioned webhook URL should answer 410 so crawlers and link checkers stop probing. A typo'd path or a resource that never existed answers 404. 410 also permits a Retry-After header in theory, though servers rarely use it; the useful signals are Cache-Control and a human-readable explanation body pointing at a replacement.

Concrete example: an API deprecates /v1/users with a Sunset header and removes it after the window. Queries to /v1/users return 410 with a body pointing at /v2/users, while /v1/users/nonsense returns 404. A knowledge base that deletes a wiki page and wants link checkers to stop flagging it returns 410 for the old slug instead of 404, which would keep the checker retrying forever.

Failure modes: returning 404 for intentionally removed resources keeps them indexed and probed indefinitely; returning 410 for never-existing paths misleads clients into treating typos as deliberate removals. Over-aggressive 410 on soft-deleted data can leak existence — the 410 itself confirms the resource once existed — which matters for GDPR erasure: a truly erased record should usually 404, not 410, so deletion is indistinguishable from never-having-existed.

Operational tradeoffs: 410 requires maintaining a tombstone of deleted URIs, which costs storage but preserves link hygiene; 404 needs no state. During API versioning, 410 on retired versions plus a Sunset header gives clients a clear migration trigger, while 404 on unknown versions keeps the version surface quiet. Logs and monitoring should separate the two codes so decommissioning events are auditable.

RSIS3/mykb relevance: mykb's own link-checker treats 404 versus 410 differently when pruning wiki links; encoding that rule here keeps the check-practices workflow consistent across sessions.
