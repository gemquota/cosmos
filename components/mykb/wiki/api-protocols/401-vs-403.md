# 401 vs 403

## Summary
401 means the client has not presented acceptable credentials; 403 means the server understood who the client is but refuses the action anyway. Choosing wrong leaks information or breaks client retry logic.

## Details
401 Unauthorized signals missing or invalid authentication: the request carried no credentials, or the presented ones failed verification. The response must include a WWW-Authenticate header describing the challenge (Bearer realm, Basic realm, Digest parameters) so the client knows how to authenticate and may retry. 403 Forbidden means authentication succeeded — the server knows the identity — but the principal is not allowed to perform the action, or the resource is off-limits regardless of identity.

The classic mechanism check: can the client retry the same request with different credentials and succeed? If yes, the code is 401; if no, 403. An unauthenticated user hitting a private endpoint should get 401, prompting a login; an authenticated user without the admin role hitting an admin endpoint should get 403. Mixing them up causes infinite login loops on the 401 path or confusing login prompts on the 403 path.

Concrete example: GET /api/users/42/comments with no token returns 401 plus WWW-Authenticate: Bearer; with a valid user token but no read scope returns 403 with an error body explaining the missing scope. An API that returns 401 for expired tokens should distinguish them from revoked tokens: a revoked token must stay rejected even after re-login flows. Some OAuth resource servers use 401 with error="insufficient_scope" (RFC 6750) rather than 403 in specific flows — a nuance worth pinning per service so clients don't cache the wrong retry behavior.

Failure modes: returning 403 for unauthenticated requests hides whether login would help and defeats client challenge handling; returning 401 for authorization failures leaks that the account exists and can feed enumeration attacks. Middleware that conflates the two turns expired sessions into 500s or redirect loops. Retry logic must treat 401 as credential refresh plus retry, and 403 as terminal — never retried blindly.

Operational tradeoffs: 403 can carry detail (which permission is missing), but that detail helps attackers map the authorization model, so many APIs return a generic 403 and log the specific reason. 401 challenges expose supported schemes, so public APIs sometimes downgrade to 404 on unauthenticated access to hide resource existence. Neither 401 nor 403 should be cached by shared caches, but misconfigured caching layers replay them anyway.

RSIS3/mykb relevance: session postmortems that distinguish authentication failures from authorization failures are reusable patterns; storing the decision rule here keeps loop-generated incident reviews consistent across sessions.
