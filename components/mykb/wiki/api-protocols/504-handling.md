# Handling 504

## Summary
504 Gateway Timeout means an upstream did not answer within the gateway's deadline. It forces explicit decisions about timeouts, retries, and whether slow work belongs in the request path at all.

## Details
504 Gateway Timeout is generated by a gateway, proxy, or load balancer when an upstream connection was established but the upstream did not produce a complete response within the configured timeout. The upstream may still be processing — the request may be running fine — but the intermediate decided the client cannot wait any longer. This makes 504 fundamentally a timeout-policy signal, not just an error.

The mechanism: the gateway has connect, first-byte, and idle timeouts. If the upstream sends nothing within the first-byte timeout, the gateway aborts the upstream connection and answers 504, logging the upstream and elapsed time. Whether the upstream keeps working depends on cancellation: if the gateway does not propagate cancellation (via HTTP/2 RST or a gRPC context), the upstream may complete work nobody will collect — a classic orphaned-request problem.

Concrete example: an API endpoint builds a heavy report in ten seconds, but the gateway's timeout is five seconds. Every request returns 504 while the backend keeps computing, wasting CPU. The fix is raising the timeout for that route, streaming partial results, or — usually better — converting the report into an async job with 202 Accepted plus a poll or webhook pattern. Client-side, a 504 after five seconds is worth one retry only if the operation is idempotent; retrying a long non-idempotent write can double-apply.

Failure modes: timeout values longer than the client's patience push 504s down to clients as plain connection errors; cancellation that is not propagated leaves zombie work consuming capacity; and blindly retrying 504s on non-idempotent endpoints duplicates side effects. Monitoring must capture the gateway timeout value and the upstream p99 latency together, since the gap is the actionable number.

Operational tradeoffs: tight timeouts bound worst-case latency and protect gateway resources but reject legitimately slow work; loose timeouts hide slow endpoints from users. The robust pattern is layered deadlines — client less than gateway less than upstream — so each layer fails fast, plus async processing for anything that cannot meet the budget. gRPC's per-call deadline mechanism exists precisely to express this contract.

RSIS3/mykb relevance: when RSIS3 loops call external services during self-improvement cycles, documenting per-call deadlines and the 504 behavior of the gateway keeps the loops from over-retrying and double-executing actions.
