# Tail Latency

## Summary
Tail latency is the delay experienced by the slowest requests — p99 and beyond. In distributed systems, a single slow backend makes many user requests slow because fan-out multiplies the worst case: with 100 parallel calls, even 1% slow backends give nearly every request a slow leg.

## Details
- Mechanism: fan-out amplification is the core effect — a request that waits on N parallel subcalls experiences the max of their latencies, so the tail of the distribution dominates; queue buildup worsens it (a slow response delays everything behind it); long tails often come from garbage collection pauses, noisy neighbors, or hot keys rather than average load.
- Concrete example: an article generated by 20 parallel tool calls — if each has a 5% chance of a 3s stall, almost every article waits 3s; hedged requests (send two, use the first response) and short timeouts cut the effective tail; replicated work and load shedding reduce queue buildup at the source.
- Failure modes: optimizing the average while the tail worsens (users feel the tail); timeouts that are too generous, so the tail propagates everywhere; hedges that double load without cutting latency; ignoring GC pauses and noisy neighbors, blaming the wrong layer; tail problems measured only at p99 while p999 is catastrophic.
- Tradeoffs: tail-latency engineering costs extra capacity and complexity (hedging, replication, careful timeout design) in exchange for consistent user experience; the alternative, accepting the tail, is cheaper and unpredictable; the mature pattern is short timeouts, hedged or replicated work for critical paths, and monitoring p99 plus p999.
- Operational notes: monitor percentile divergence, size hedges from real tail data, and reduce queue buildup before adding capacity.
- RSIS3 relevance: multi-agent fan-out has the same tail problem — one slow model call delays the whole article — so hedges and timeouts belong in the loop design.
