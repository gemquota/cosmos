# mykb

mykb is **RSIS3's long-term memory**: a persistent, human-readable semantic
knowledge database built on the Open Knowledge Format (OKF) and Obsidian wiki
conventions. Every article is markdown with YAML frontmatter; links are the
graph.

Start from [[Home]] or the [[wiki/index|Wiki Index]]. New to the
knowledge base? Read the [[ops/conceptual-guide|mykb for Humans — Conceptual
Guide]] first: it explains the mental model, the layers, and how to navigate.

## Roles

- **Memory store** — pulses, decisions, sessions, reflections (see
  [[ops/rsis3-memory-bridge|RSIS3 Memory Bridge]])
- **Semantic database** — typed, tagged, timestamped articles plus an emergent
  link graph (`graph.json`)
- **Research corpus** — sources and syntheses from acquisition rounds (see
  [[ops/knowledge-acquisition|Knowledge Acquisition]])

## Layout

- `raw/`: original material and archives
- `wiki/`: processed knowledge (concepts, sources, syntheses, memory areas)
- `templates/`: note templates
- `ops/`: workflows, schema, prompts, reports
- `daily/`: daily notes
- `graph.json`: static knowledge-graph export (nodes + edges)
- `files.json`, `wiki/index.json`: static indexes for hosting without the daemon
  (`files.json` is enriched: `{path, type, title, tags}` per file, driving the
  Content/Meta split, Type grouping, and home metrics)

## Operations

- `okf validate .` — OKF conformance
- `okf lint .` — curation quality
- `python3 .wiki-daemon/build_graph.py` — regenerate the link graph
- `python3 build-index.py` — regenerate `wiki/index.json`
- `python3 .wiki-daemon/build_files_index.py` — regenerate `files.json`

## Guidance workflow

The **Guide** tab in `index.html` (`#guidance`, formerly the stub auditor) is
mykb's general guidance UI: it steers the research and nature of the knowledge
base — not just stub triage.

- **Direction** — live area health: pages / stubs / stub % / avg words per
  wiki area, ranked by stub burden, so the next acquisition & enrichment pass
  targets the thinnest, most backlogged domains. Static data ships in
  `guidance.json` (regenerated by `build_stub_audit.py`); live mode serves
  `GET /api/v2/guidance`. The same data includes **wanted links** — red
  links (`[[target]]` with no existing page) ranked by inbound count, i.e.
  missing pages the wiki itself points to; each offers a one-click “add to
  research queue”.
- **Research & Feedback queue** — queue wanted pages, research directions,
  open questions, and page-level notes (suggestion / correction / priority /
  note) with P1–P3 priority. Items persist to
  `.wiki-daemon/buffers/guidance-queue.json` via
  `POST /api/v2/guidance/queue` (static pages fall back to localStorage +
  download); a floating **Feedback** button pre-fills the current page.
- **Stub triage** — the original auditor is now a section of the Guide tab:
  Keep / Enrich 1×–3× / Categorize / Archive / Delete for pages with
  frontmatter `status: stub`, plus the pre-archived junk entities under
  `raw/archive/junk-entities-*` (flagged `junk`, Keep/Delete only). Live data
  comes from `GET /api/v2/stubs` (fast thanks to a HEAD-keyed date cache);
  statically it falls back to `stub-review.json` / `stub-index.json`.
- **Queue answers** — `Save queue` POSTs stub decisions to
  `POST /api/v2/stubs/queue`, which writes
  `.wiki-daemon/buffers/stub-audit-queue.json`. Without a live server it
  downloads the same JSON for you to place in `buffers/`.
- **Inference pass** — `python3 .wiki-daemon/drain_stub_queue.py --plan`
  previews the queue; `--apply` executes the mechanical decisions
  (categorize / archive / delete via `git mv` / `git rm`) and emits an
  enrichment manifest at `.wiki-daemon/buffers/stub-audit-inference.json`,
  merging the guidance queue in as `guidance.research` (wanted pages /
  directions / questions) and `guidance.feedback` so the same pass seeds new
  pages and honours human direction.
- **Research drain** — `python3 .wiki-daemon/drain_guidance.py --plan`
  previews what the guidance queue implies; `--apply` scaffolds `wanted`
  items into `wiki/<area>/<slug>.md` stubs and `question` items into
  `wiki/questions/`, then writes a research manifest at
  `.wiki-daemon/buffers/guidance-inference.json` (created paths, remaining
  directions, page feedback) for the next session. Existing files are never
  overwritten; scaffolds carry `status: stub` + `source: ["guidance-queue"]`
  so they flow into normal stub triage. Live UI buttons mirror
  `POST /api/v2/guidance/plan|apply`.
- **Rebuild** — `python3 .wiki-daemon/build_stub_audit.py` regenerates
  `stub-review.json` + `guidance.json`.
- **CLI** — `cosmos guidance open` (live Guide tab), `cosmos guidance status`,
  `cosmos guidance build`, `cosmos guidance plan / apply` (research drain);
  `cosmos stubs plan / apply` wrap the stub drain; `cosmos start mykb` /
  `cosmos stop mykb` manage the daemon.
- **Dashboard** — the unified dashboard embeds the Guide tab under
  **MyKB → Guidance**; its drain panel replicates
  `cosmos stubs plan / apply / build` via
  `POST /api/v2/stubs/queue/plan`, `/queue/apply`, and `/build` (plus
  `GET /api/v2/stubs/queue` for status). The SPA tries same-origin then
  `http://localhost:8765`, so it works embedded on any origin.
