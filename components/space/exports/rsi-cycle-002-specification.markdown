### Round 1: Direct Associations

**Q 3.1.1** — What direct associations exist between entities? Which entities reference, point to, or are linked to which others?

<details>
<summary>Answer (1409 chars)</summary>

> In the codebase, these associations manifest as TypeScript interfaces in `src/types/index.ts` and as foreign-key-style string fields on each entity. Framework → Series is implemented as `Framework.series: Series[]` (strong ownership), while Answer → Question is `Answer.questionId: string` (weak reference). The bidirectional containment (Series knows its parent Framework) is implemented by each child holding a `parentFrameworkId: string` — this is redundant with the parent holding the array, but it enables efficient lookups from child to parent without scanning the parent's array. In `src/engine/session-manager.ts`, the Session aggregate holds `answers: Map<string, Answer>` and `artifacts: Record<string, Artifact>`, making the composition relationship explicit. The weakest reference is Export → Session: an Export only stores `sessionId: string`, and if the Session is deleted, the Export becomes orphaned. In practice, `src/storage/filesystem.ts` doesn't enforce referential integrity, so orphaned references are possible. A defensive pattern would be to add a `validateIntegrity()` method that walks all Export references and flags missing Sessions. For implementation, use `Map<string, T>` for the one-to-many relationships inside Session (Answers, Artifacts) and plain arrays for the Framework hierarchy (Series[], Round[], etc.) since the Framework is loaded once and never modified at runtime.

</details>

> **Selection:** Moderate — roughly one association per entity on average

**Q 3.1.2** — What is the nature or type of each association? Is it a use, creation, ownership, or communication link?

<details>
<summary>Answer (1599 chars)</summary>

> In the TypeScript implementation, these five association types are distinguished by their access patterns in the Engine. CONTAINS is implemented via direct property access: `framework.series[i]` or `round.questions` — no lookup needed, O(1) access. REFERENCES use ID-based lookup: `session.getAnswer(questionId)` calls `this.answers.get(questionId)` which is a Map lookup, O(1) amortized. PRODUCES is the same as CONTAINS at the Session level (Session produces Answer, Answer is stored in Session.answers Map), but the semantic difference matters for lifecycle management — when a Session is deleted in `src/storage/filesystem.ts`, its Answers are deleted with it (composition), but referenced Questions in the Framework are not (references survive). CONSUMES is implemented in `src/engine/dependency-resolver.ts` where the resolver checks that required artifact keys exist in the session's artifact dictionary before allowing a Series to start. The implementation uses `Object.keys(session.artifacts)` to validate that all keys declared in `series.consumes` are present. DEPENDS_ON is also in the dependency resolver, enforced via topological sort of the Series graph before the session begins — `buildExecutionOrder(framework)` returns the Series IDs in valid order. A practical gotcha: the DEPENDS_ON and CONSUMES declarations on each Series in the framework JSON must be kept in sync. If Series 3 declares `consumes: ['entities']` but doesn't declare `deps: ['series-2']`, the dependency resolver will catch the missing dependency, but the error message should clearly explain the inconsistency.

</details>

> **Selection:** 2–3 distinct relationship types (e.g., owns, produces, references)

### Round 2: Hierarchical and Containment Relationships

**Q 3.2.1** — What parent-child, containment, or hierarchical relationships exist? Which entities are within, belong to, or are part of others?

<details>
<summary>Answer (1613 chars)</summary>

> The two hierarchies are implemented in separate code paths. The Framework hierarchy is loaded in `src/data/framework-loader.ts` as a nested object: `Framework { series: Series[] }` where `Series { rounds: Round[] }`, `Round { questions: Question[] }`, `Question { choices: Choice[] }`. This is a straightforward recursive structure — the loader reads JSON and the TypeScript types enforce nesting. The Project hierarchy lives in `src/engine/session-manager.ts` where `Project { sessions: Session[] }` and `Session { answers: Map<string, Answer>, artifacts: Record<string, Artifact>, exports: Export[] }`. The key implementation detail is that `Session.currentQuestionId: string` is the bridge between hierarchies — it points into the Framework tree by question ID, and the `src/engine/question-router.ts` uses this ID to navigate the Framework structure (find which Round, which Series, advance to next). The progress tracking in `src/engine/progress.ts` works on the Framework tree: it tracks which Questions have been answered by checking `session.answers.has(question.id)`. This is efficient because the check is O(1) per question. A practical concern: the `snapshot-manager.ts` serializes both hierarchies to disk. When resuming, it deserializes the Session hierarchy first, then re-loads the Framework from the original JSON file. If the Framework file was modified between sessions, question IDs might still match but the structural position could differ — the question-router needs to handle this gracefully by validating that the currentQuestionId still resolves to a valid position in the Framework tree.

</details>

> **Selection:** Shallow hierarchy (1–2 levels) — simple containment chains

<summary>Answer (1446 chars)</summary>

> The entity interfaces in `src/types/index.ts` use flat types with no inheritance. For example, `Series` and `Round` both have `id: string` and `name: string` properties, but these are independently declared rather than inherited from a common `Identifiable` base. This is the TypeScript convention for data transfer objects — you avoid base classes because they complicate JSON serialization (you need to handle prototype chains) and make type narrowing harder (TypeScript's type guard works best with flat types). The shared behaviors are implemented as standalone functions: `validateEntity(entity: unknown): entity is Series` in `src/engine/validator.ts`, `serializeToJSON(entity: Series | Round | Question): string` as a generic function. The Series-specific behavior (what it consumes, what it produces) is configured in the framework JSON files, not in TypeScript types. For example, in `src/data/artifact-mapping.ts`, the `ARTIFACT_DEFINITIONS` record maps artifact keys to their schemas — this is the closest thing to a 'type hierarchy' for artifacts, and it's entirely data-driven. To add a new artifact type, you add an entry to `ARTIFACT_DEFINITIONS` and update the relevant Series' `produces` array. No new TypeScript types needed. The practical implication: the artifact type system is extensible without code changes, which is important for community contributions (users can define custom artifact types by editing framework JSON).

</details>

> **Selection:** Simple inheritance — a few parent types with child specializations

### Round 3: Causal and Dynamic Relationships

**Q 3.3.1** — What causal, temporal, or triggering relationships exist? Which entities cause changes in, or are triggered by, others?

<details>
<summary>Answer (1659 chars)</summary>

> The causal chain is implemented as a pipeline in `src/engine/core.ts` where the main loop calls `processSeries(framework, session, seriesIndex)` sequentially for each Series in execution order. Within each Series, `completeRound()` processes questions in order, and after each answer is recorded, `extractArtifacts(answer, session)` is called synchronously. The temporal ordering is enforced by the `question-router.ts` which maintains a `currentRoundIndex` and `currentQuestionIndex` — advancing is the only valid operation (no going back to previous questions within a session, though re-answering by restarting is possible). The triggering mechanism for Series transitions is in `src/engine/dependency-resolver.ts`: `canStartSeries(series, session)` checks that `series.consumes.every(key => key in session.artifacts)`. This is a synchronous check, not an event listener — the system polls for readiness rather than reacting to events. For the artifact dictionary, which 'grows monotonically,' the implementation uses `session.artifacts = { ...session.artifacts, ...newArtifacts }` — a shallow merge. This means if two Series produce artifacts with the same key, the later one overwrites the earlier one. The framework JSON should ensure artifact keys are unique, but there's no runtime enforcement. A defensive pattern would be to use `Map<string, Artifact>` and throw on duplicate keys: `if (session.artifacts.has(key)) throw new Error('Duplicate artifact key')`. The snapshot system in `src/engine/snapshot-manager.ts` captures the artifact dictionary state after each Series completes, enabling resume-from-snapshot without re-running completed Series.

</details>

> **Selection:** Direct causation — entity A creates or changes entity B in a predictable chain

**Q 3.3.2** — What dependency chains, prerequisites, or ordering constraints exist? Must some entities exist before others can be created or used?

<details>
<summary>Answer (1648 chars)</summary>

> The dependency ordering is implemented in `src/engine/dependency-resolver.ts` with a topological sort algorithm. The `buildExecutionOrder(framework)` function constructs a graph from the `series.deps` arrays and returns a valid execution order. For SPACE's 7-Series framework, the order is typically [1, 2, 3, 4, 5, 6, 7] (linear), but the framework JSON could define a different dependency graph (e.g., if Series 3 and 4 were independent of each other but both depended on Series 2, they could run in parallel — though the CLI is sequential so this parallelism isn't exploited). The prerequisite validation happens at two points: (1) before starting a Series (`canStartSeries()` checks `series.deps.every(dep => isSeriesComplete(dep))`) and (2) before accessing an artifact (`session.getArtifact(key)` throws if the key doesn't exist). The ordering within a Series is enforced by `question-router.ts` which tracks `currentRoundIndex` and only advances to the next round after `completeRound()` returns. For the '67 Questions across 7 Series' structure, the prerequisite chain means the user must complete all Questions in Series 1 before seeing any Question in Series 2. The implementation uses `framework.series[i].rounds` to navigate the structure. A practical edge case: if a user starts a session, completes Series 1-3, then updates the framework.json to add new Questions to Series 1, the session should still be resumable because the session stores completed Questions by ID, and new Questions simply appear as unanswered. The dependency resolver doesn't need to re-validate completed Series — it only checks Series that haven't started yet.

</details>

### Round 4: Composition and Constraints

**Q 3.4.1** — What rules govern how relationships can change? Can associations be created, deleted, or modified at any time, or are there restrictions?

<details>
<summary>Answer (1455 chars)</summary>

> The mutation rules are implemented through TypeScript's type system and runtime validation. Framework loading in `src/data/framework-loader.ts` returns `Framework` objects that are never modified — the Engine receives them as function parameters (pass by value in terms of structure) rather than storing references to mutable objects. In `src/engine/session-manager.ts`, `session.answers.set(questionId, answer)` replaces an existing answer if the questionId already exists — this is the 'replace-only' semantics. The artifact dictionary is updated via `session.artifacts = { ...session.artifacts, ...newArtifacts }`, which also replaces on key collision. There's no explicit deletion: if you want to 'remove' an answer, you set it to an empty answer object `{ questionId, text: '', followUpChoiceId: null }`. For Framework versioning, `src/data/framework-loader.ts` validates the framework JSON against a schema at load time — if a new version has structural changes (different number of Series, new required fields), the validator will catch it and either adapt gracefully or abort with an error. The Export entities in `src/export/index.ts` are write-once: once a file is written to disk, it's not modified. If you re-export, the old file is overwritten entirely. The filesystem storage in `src/storage/filesystem.ts` uses `fs.writeFileSync()` which atomically replaces the file contents — no partial writes, no corruption risk from interrupted writes.

</details>

> **Selection:** State-gated — relationships can only change when entities are in certain states

**Q 3.4.2** — How do relationships compose or chain across entities? Can indirect relationships be inferred from direct ones?

<details>
<summary>Answer (1963 chars)</summary>

> The indirect relationship traversal is implemented as a series of accessor methods across the codebase. In `src/export/formatters/markdown-exporter.ts`, provenance tracking works by following the chain: export the Artifact → include `artifact.sourceQuestionId` → look up the Question text → include the Question text as a 'Source:' annotation in the Markdown output. The key implementation for cross-boundary traversal is in `src/engine/progress.ts`: `isQuestionAnswered(question, session)` checks `session.answers.has(question.id)` — this is the primary cross-boundary check, happening for all 326 questions during progress computation. 2. File locking: Windows locks open files. The atomic write pattern (write .tmp, rename) handles this, but if another process has state.json open, the rename may fail with EBUSY.
3. Case sensitivity: Windows filesystems are case-insensitive by default. Project 'MyProject' and 'myproject' resolve to the same directory. The codebase should normalize project names to lowercase to avoid confusion.

macOS-specific: Apple Silicon (ARM64) runs Node.js natively. No Rosetta translation needed. The crypto module works identically.

Linux-specific: File permissions are stricter. The ~/.space/ directory needs read/write permissions for the current user. If SPACE is installed via npm -g, the dist/ files may be owned by root. The CLI should check permissions on startup and warn if ~/.space/ is not writable.

For CI testing on GitHub Actions, the workflow should run on ubuntu-latest (primary), macos-latest (secondary), and windows-latest (tertiary) with Node.js 18 and 20.

**Q 5.3.3** — What availability, uptime, and disaster recovery targets are required?

<details>
<summary>Answer (1482 chars)</summary>

> Reliability mechanisms in the SPACE codebase: (1) The `snapshot-manager.ts` creates snapshots with trigger types `'round_complete' | 'series_complete' | 'manual' | 'auto'` — each snapshot stores the full `SessionState` in a separate file, providing crash recovery up to the last snapshot boundary. (2) `auto_save_interval_ms` (default 10000ms from `src/config/defaults.ts`) triggers periodic persistence via the engine's save mechanism. The SQLite adapter adds WAL mode and transactional writes but is not the default. Practically, for a single-user tool, the combination of auto-save + snapshots + filesystem atomic writes provides adequate durability.
